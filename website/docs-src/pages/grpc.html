MockHub answers gRPC calls from stubs. Upload a protobuf descriptor set for your services and write each answer as JSON. MockHub converts it to the protobuf message the client expects.

To see it working first, install the Inventory — gRPC from a descriptor set example (Examples in the sidebar). It serves inventory.v1.StockService with a unary, a server-streaming and a client-streaming method, a templated answer, gRPC statuses and a stub that matches metadata. Try it with grpcurl -plaintext -d '{"sku":"sku-7"}' localhost:8080 inventory.v1.StockService/GetItem. Because a service belongs to one project, the example can be installed once per server.

Upload a descriptor set

gRPC messages are binary, so MockHub needs your service definitions. Build a descriptor set from your .proto files with protoc:

protoc --include_imports --descriptor_set_out=library.dsc library.proto

--include_imports puts every imported file in the set. Google's well-known types, such as Timestamp, Duration and the wrappers, work even without it. Buf users can run buf build -o library.dsc.

In a project's Import / export tab, drop the file on gRPC services. MockHub lists each service with its methods and starts answering them right away. No restart is needed. Create stubs adds one stub per method, each answering with an example message built from the response type.

Descriptors are part of the project. They're saved in the data folder, loaded again on restart and included in backups.

gRPC stubs

Choose gRPC stub in the Stubs tab, or gRPC as the service type in the editor. Then pick the service and method. Picking a method fills in an example response and an example request. A gRPC stub in JSON:

{
  "request": {
    "method": "POST",
    "urlPath": "/library.v1.BookService/GetBook",
    "bodyPatterns": [{ "equalToJson": "{\"id\": \"7\"}", "ignoreExtraElements": true }]
  },
  "response": { "status": 200, "jsonBody": { "id": "7", "title": "Dune", "year": 1965, "genre": "FICTION" } },
  "metadata": { "mockhub": { "type": "grpc" } }
}
  • Request message. The request message arrives as JSON, so match it with the usual body matchers. JSON equals with extra fields allowed is the most useful, and JSONPath works too. Leave the body empty to answer every call to the method.
  • Metadata. gRPC metadata such as authorization can be matched like headers.
  • Response message. Protobuf JSON, with either the proto field names (published_at) or their lowerCamel form (publishedAt). Enums are written by name, 64-bit numbers as strings, and Timestamp as "2026-01-01T00:00:00Z".
  • Templating. Turn on response templating to build the answer from the request: {{jsonPath request.body '$.id'}} echoes a field.
  • Path. The path is never prefixed with the project path, because gRPC clients always call /package.Service/Method.

Errors and status codes

Set Status to any gRPC code, such as NOT_FOUND, INVALID_ARGUMENT, UNAUTHENTICATED or UNAVAILABLE, and optionally a message. The client gets that status and message with no response message. In JSON these are two response headers:

"response": { "status": 200, "headers": { "grpc-status-name": "NOT_FOUND", "grpc-status-reason": "No book 404" } }

A call that no stub matches gets UNIMPLEMENTED. Use priority to let an error stub for one id win over a general stub for the method.

Streaming methods

Method kindHow MockHub answers
UnaryOne request, one response message from the matching stub.
Server streamingThe stream holds one message, the stub's response, then completes.
Client streamingEach message the client sends is matched in turn. The first one that matches a stub decides the answer.

Calling the mock

gRPC runs over HTTP/2. MockHub serves it in plaintext (h2c) on its own port, next to the HTTP mocks. Server reflection is on, so grpcurl and tools like Postman can find the services without the .proto files:

grpcurl -plaintext localhost:8080 list
grpcurl -plaintext -d '{"id": "7"}' localhost:8080 library.v1.BookService/GetBook

A gRPC stub's editor shows this command, with its example request, where other stubs have Try it. Point your app's gRPC channel at the same host and port with TLS turned off. Calls appear in the project's history like other requests.

A reverse proxy in front of MockHub must forward HTTP/2 for gRPC to work, for example with nginx's grpc_pass. A proxy that only speaks HTTP/1.1 to MockHub breaks gRPC calls, while the UI and HTTP mocks keep working.
