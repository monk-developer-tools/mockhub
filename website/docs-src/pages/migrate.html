MockHub runs your WireMock mappings unchanged: the same matchers, templates and body files, on the same URLs. Pick the way that fits what you have.

A folder of mappings

For mappings inside an app, such as src/test/resources/wiremock, or a small standalone server.

  1. Zip the folder that holds mappings and __files. Where it sits inside the zip doesn't matter.
  2. Create a project and import the zip under Import & export → WireMock folder.
  3. In the project's Settings, turn on Answer at the root. URLs, and templates that count path segments such as {{request.pathSegments.[0]}}, then behave exactly as before.
  4. Point your services at MockHub instead of the old WireMock host.
zip -r wiremock.zip src/test/resources/wiremock

A whole repository of mappings

For a Git repository with a folder per team, thousands of stubs, files that hold many stubs each, and a pipeline that restarts WireMock after every merge. There are two ways in, and both give the same responses as before.

Run MockHub on the folder. Copy the folder that holds mappings and __files and use the copy as MockHub's data folder. Every stub answers at once. Use a copy rather than your Git checkout, because changes made in MockHub are written back to these files.

cp -R acme-mocks/mock /srv/mockhub-data
docker run -d --name mockhub -p 8080:8080 \
  -e MOCKHUB_USERS="admin:change-me:admin" \
  -v /srv/mockhub-data:/data abhaypratap/mockhub

The stubs are listed under Server → Stubs outside any project. To manage them in the UI, move them into a project that answers at the root:

API=http://localhost:8080/__admin/mockhub/api
AUTH="admin:change-me"
PROJECT=$(curl -s -u $AUTH $API/projects -H 'Content-Type: application/json' \
  -d '{"name":"Acme mocks","root":true}' | jq -r .id)
curl -s -u $AUTH $API/stubs/unassigned | jq -r '.[].id' | while read id; do
  curl -s -u $AUTH -o /dev/null -X POST "$API/projects/$PROJECT/adopt/$id?prefix=false"
done

Or import it as a zip into a project with Answer at the root turned on, as for a single folder. A zip can hold up to 20,000 files and 200 MB, with up to 10 MB per file. MockHub lists any body file a mapping needs that the zip doesn't have.

cd acme-mocks && zip -r ../acme-mocks.zip mock

What carries over

In your mappingsIn MockHub
Files with one stub, or many ({"mappings": [...]})Both load. A file with many stubs is split into one file per stub, in the same folder, the first time one of its stubs changes.
Body files in folders, ./ and / pathsUnchanged. An import keeps the folders and points each stub at the project's copy.
File names built from the request, e.g. ./orders/{{request.pathSegments.[1]}}.jsonUnchanged
Empty body filesServed as empty responses
Several stubs that match with the same priorityThe same one wins after edits and restarts. The order is kept in data/mockhub/mapping-order.txt.
Matchers, priorities, scenarios, faults, delays, proxies, webhooksUnchanged. Proxies need network access to the target.
Response templates and transformerParametersUnchanged on stubs with "transformers": ["response-template"]
Very long URLsSaved with a shortened file name; the stub is unchanged

Before you switch

  • Templating for every stub. If your WireMock ran with --global-response-templating, start MockHub with WIREMOCK_OPTIONS=--global-response-templating, or add "transformers": ["response-template"] to those stubs.
  • Missing body files. A mapping that points at a file that doesn't exist answers with a 500 in WireMock and in MockHub. The import lists them, so fix them first.
  • Runtime changes. Calls to /__admin/mappings keep working with a MockHub token or HTTP Basic auth.
  • Compare. Run both side by side for a day and send the same calls to each. The Requests tab shows near misses for anything that didn't match.
  • The restart job. Changes go live immediately, so a pipeline step that restarts WireMock after each merge isn't needed. Keep a copy with backups, or export the project as WireMock mappings.
