The Requests tab shows every call a project received, newest first, and keeps them on disk so you can search days of traffic, not just the last few minutes. It updates live while Live is ticked.

Inspect: each request beside its answer

The Inspect tab is the view of the free webhook catcher, inside a project. Projects made from the Webhook testing, HTTP traffic monitoring, HTTP echo and Local tunnel cards open on it. On the left, requests arrive live, with search and method and status filters; on the right, Request and answer shows the method, path, query, headers and body that came in beside the status, stub, headers and body that went out, and any callouts it sent.

  • Send test posts a sample event to the project's receiver, so you can see the view work before a real webhook arrives.
  • Make a stub from it opens the stub editor filled in from the request, to answer it your own way.
  • Copy as cURL, Replay in the Playground, and Copy link to share one request with your team.

Inspect shows the newest 100 requests; the Requests tab below searches all of the history, draws the traffic chart and exports HAR.

Traffic at a glance

The chart at the top counts calls over the last 5 minutes, 15 minutes, hour, 6 hours or 24 hours, with unmatched calls in amber. Beside it are the total, the unmatched count, the average and the peak requests per second. Choose 30d for one bar per day over the last 30 days. Hover a bar to see its exact numbers. Drag across the chart to list only the requests in that span; clear the time chip to go back.

Search and filter

Type in the search box to find text anywhere in the URL, the headers or either body. Narrow further with:

FilterExamples
MethodPOST
Status404, a class like 4xx, or a range like 500-599
Matched or notOnly calls that found no stub, which is the quickest way to find a missing one
StubOnly calls one stub answered
HeaderX-Tenant to find calls that sent it, or X-Tenant:acme to find a value

The chips under the filters count what matched by status class, and how many found no stub. Click one to filter by it. Filters live in the page address, so you can bookmark a search or send it to a teammate. Results come 100 at a time; use Older and Newer to page.

Look at one request

Click a request to see its status, the stub that answered, timing, both sets of headers and both bodies (JSON is formatted). From there you can:

  • Create stub from this request: opens the stub editor already filled in with the method, path, query and body.
  • Replay in Playground: sends the same call again and lets you change it first.
  • Copy it as cURL, HTTPie, JavaScript, Python, Java, C# or Apex.
  • See the callouts the request triggered, with their result.

For an unmatched request, MockHub also lists the closest stubs and how near each came, so you can spot a typo in a path or a missing header.

Export as HAR

Export HAR downloads what the current filters match, up to 500 requests, as a HAR 1.2 file. Open it in your browser's developer tools, in Postman or Insomnia, or attach it to a bug report.

Inspect third-party webhooks

Select Catch all webhooks and give the other service the URL shown. MockHub adds a low-priority stub that answers 200 to anything, so every webhook the service sends lands in the history.

How long history is kept

Each project keeps 7 days of requests and callouts, up to 200 MB. When a project goes over, its oldest hours are dropped first. Change both with MOCKHUB_HISTORY_DAYS and MOCKHUB_HISTORY_MAX_MB (see Configuration). Bodies longer than 64 KB are cut, and binary bodies are stored as their size only. Clear history deletes a project's requests at once. History stays on the server's disk under /data/mockhub/history; it isn't part of backups.

The AI assistant can search the same history: ask it something like "Which calls failed in the last hour, and why?"

Masked headers

Organisation managers can list headers whose values nobody should see, such as Authorization or X-Api-Key, under Teams & people → Settings → Masked headers; Add the usual secret headers fills in the common ones. Names match in any case. Their values then show as •••••• for everyone in every project of the organisation: the Requests tab and its live log, a request's details, HAR exports, and the admin API. New requests are masked before they are written to disk, and requests recorded earlier are masked whenever they are shown. A search for a masked value finds nothing. WireMock's own /__admin/requests journal, which only server admins can read, isn't masked. From a script, PUT /__admin/mockhub/api/orgs/{orgId} with {"maskedHeaders": ["authorization", "x-api-key"]}.
