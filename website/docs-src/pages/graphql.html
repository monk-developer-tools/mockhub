MockHub mocks a GraphQL API from its schema. One endpoint answers every query and mutation with data that follows the schema, and you add fixed answers for the operations a test cares about.

Import a schema

In a project's Import / export tab choose GraphQL, then drop a .graphql file or paste the schema. MockHub reads:

  • SDL, the schema language: type Query { book(id: ID!): Book }.
  • An introspection result, the JSON a GraphQL server returns for the introspection query, with or without the outer data.

The import creates one stub, GraphQL: <name>, at /graphql (change it under Endpoint path) with priority 10, so fixed answers win. Directives the schema uses but doesn't declare, such as federation's @key, are ignored.

How answers are made

The endpoint runs each query against the schema, so a client gets exactly the fields it asked for, in the shape it expects. Validation errors come back as GraphQL errors, the way a real server sends them.

In the schemaThe answer
String, Int, Float, IDRealistic values chosen by field name: email gets an e-mail address, name a person's name, city a city, price an amount.
Custom scalarsBy scalar name: DateTime, Date, UUID, URL, Email, JSON; others get text.
Enums, interfaces and unionsOne of their values or types.
Lists3 items, or as many as a first, last, limit, take, size or count argument asks for, up to 20.
Arguments and inputsCopied into fields with the same name: book(id: "42") answers with id 42, and borrow(input: {borrower: "Ada"}) answers with borrower Ada.

The same query with the same arguments always gets the same answer, so tests stay stable; another id gets other data. Requests can be POST with JSON (query, operationName, variables), a batch array of up to 20 operations, POST with Content-Type: application/graphql, or GET with ?query=. Introspection works, so GraphiQL, Apollo tools and code generators can read the mock's schema.

Fixed answers for an operation

A GraphQL stub can match an operation name and, optionally, some variables. Choose GraphQL stub in the Stubs tab, or GraphQL as the service type in the editor:

"request": {
  "method": "POST",
  "urlPath": "/graphql",
  "bodyPatterns": [
    { "matchesJsonPath": "$[?(@.operationName == 'Book')]" },
    { "matchesJsonPath": { "expression": "$.variables", "equalToJson": "{\"id\": \"404\"}", "ignoreExtraElements": true } }
  ]
}

Only the variables you list must match, so {"id": "404"} also matches a request that sends more. The operation name comes from the request's operationName, which Apollo, urql, Relay and most other clients send for named operations. Answer with any JSON, for example {"data": {"book": null}, "errors": [...]}.

GraphQL console

A GraphQL stub's editor has a console instead of Try it. Choose an example operation, written from the schema with its required variables, change the query and variables, and run it against the mock. Save answer as a stub turns the answer into a fixed stub for that operation name and those variables, ready to edit.
