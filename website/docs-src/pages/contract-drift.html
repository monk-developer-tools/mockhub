Attach a project's OpenAPI document and MockHub compares every recorded call with it. Where traffic and contract disagree (a path the contract doesn't have, a missing required header, a response body that doesn't fit its schema), the Contract tab shows it, grouped, with how often it happened and an example call. Use it to keep mocks honest, or put MockHub in front of a real service with a proxy stub and see where the service has drifted from its own documentation.

Attach a contract

  • When you import: in Import & export, pick OpenAPI / Swagger and leave Keep it as the project's contract ticked.
  • On the Contract tab: upload a .json, .yaml or .yml file, paste it, or give the URL of the document.

OpenAPI 3.0, 3.1 and Swagger 2 are supported, up to 5 MB. Paths are matched with and without the path of the first server URL (or Swagger's basePath), so /v1/orders and /orders both match a contract served from https://api.example.com/v1. If calls arrive without a prefix the contract's paths have, such as /api/v1, fill in Prefix the traffic leaves out; an import that strips a prefix keeps it there for you.

What is checked

FindingWhen
Path not in the contractNo path template matches. Numbers, UUIDs and long hex ids in the path are shown as {id} so the same route groups together.
Method not in the contractThe path exists but not for this method. OPTIONS preflights are ignored.
Query parameter not in the contractA query parameter the operation doesn't list.
Header not in the contractA custom X- request header the operation doesn't list. Proxy and tracing headers such as X-Forwarded-For, X-Request-Id and X-B3-* are ignored, and so are API key headers from the security schemes.
Required parameter missingA required query, header or path parameter is absent.
Parameter doesn't match its schemaA query, header or path value has the wrong type, is out of range or isn't in its enum.
Request body problemsA body the operation doesn't describe, a missing required body, a content type it doesn't list, or a JSON body that doesn't fit its schema.
Status code not in the contractThe answer's status isn't listed, nor its range (4XX) nor default.
Response content type and bodyA content type the response doesn't list, a body where the contract describes none, or a JSON body that doesn't fit its schema.

Schemas are checked with JSON Schema, following $refs to components/schemas (or definitions) and OpenAPI's nullable. Each schema problem is its own finding, such as 200 $.total: string found, number expected, with array positions written as [*] so they group. Response checks only apply to calls a stub answered, including proxy stubs that pass the call to a real service; MockHub's own "no stub matched" answers are skipped. Bodies over 64 KB are only partly recorded, so their schema isn't checked.

The Contract tab

  • Checks run every 5 minutes on traffic recorded since the last check. Check now runs one at once; Recheck all forgets the findings and checks all recorded traffic again (up to the last 200,000 calls in your history retention).
  • Each finding shows how many calls had it, when it was first and last seen, and a link to those calls in the request log.
  • Mark expected moves a finding out of the open list and stops notifications for it. Marks are kept when you recheck or replace the contract; Reopen brings it back.
  • Up to 500 different findings are kept per project. After that, new kinds are ignored until you recheck.
  • Download gives the stored contract as YAML. Replace attaches a new version and checks all traffic against it.

Viewers can see findings and run Check now. Attaching, replacing, marking and patching need the editor role.

Fix the contract with the assistant

With the AI assistant turned on, tick the findings that the contract should accept (or none, for all open ones) and choose Suggest a patch. MockHub sends the findings, up to five example calls and the parts of the contract they touch, and asks for the smallest JSON Patch that documents them. The result is applied to a copy and shown as a diff. Nothing changes until you choose Apply to the contract, which saves the new version and checks all traffic again. A patch that doesn't fit the contract is refused, and you can ask again. Leave out findings that are client bugs rather than contract gaps.

Get told about new drift

Set Webhook for new drift to an http or https URL. When a check finds kinds of drift it hasn't seen before (and that aren't marked expected), MockHub POSTs:

{
  "event": "contract.drift",
  "at": "2026-11-05T10:05:00Z",
  "project": { "id": "…", "name": "Orders" },
  "newFindings": 1,
  "url": "https://mockhub.example.com/__admin/mockhub/ui/projects/…/contract",
  "findings": [
    { "kind": "UNDOCUMENTED_PATH", "label": "Path not in the contract", "method": "GET", "path": "/refunds/{id}", "detail": "", "count": 3 }
  ]
}

Up to 20 findings are listed. url is only included when MOCKHUB_PUBLIC_URL is set. The webhook follows the same address rules as callouts: private and local addresses are refused unless MOCKHUB_CALLOUT_ALLOW_PRIVATE=true. If it fails, the Contract tab says why. Slack, Teams and similar tools can take this through an incoming-webhook bridge. MockHub doesn't send e-mail.
