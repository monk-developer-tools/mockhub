A webhook bin is a URL that records every request sent to it and shows each one beside the answer it got. It needs no account. The page is a console: the top bar shows the bin URL and where requests go, with Rules, Routing, Share, My bins and, when available, AI each opening its own dialog. Below it is the request log; until the first request arrives, Send a test webhook sends a sample payment event so you can see how it looks. Use the free webhook catcher on the demo, or turn on MOCKHUB_PUBLIC_TOOLS on your own server (see Public tools).

What a bin keeps

Send any method to /__public/bins/{id} or any path under it. The bin keeps every request with its method, path, query, headers, body (up to 64 KB) and the answer it sent back: status, headers, body, how long it took and what produced it. There is no request count limit. A bin holds up to 50 MB in files of 10 MB; past that it drops its oldest file. The list loads 100 requests at a time, and Load older requests pages back.

Working with the log

  • Search and filter: the box above the list finds text in the path, query, headers, body, event and rule name; the menus narrow to one method or a status class such as 4xx. Older requests on disk are searched too.
  • Raw and Pretty switch a JSON body between how it arrived and indented; Copy body copies it as it arrived.
  • Multipart and binary bodies: a multipart/form-data request lists its fields and files, and each file has Download, byte for byte. Any other body that isn't text is kept as bytes and can be downloaded whole.
  • Open rule beside an answer opens the rule that gave it.
  • Make a rule from it opens a new rule that matches the request's method and path (and its event) and answers with what it got.
  • Share this request copies a link that shows that one request and its answer, nothing else of the bin, while the bin lives. Keys differ per request.
  • Delete removes one request; Clear removes them all.
  • Export saves the newest 1,000 requests that match the filter as HAR, which browser dev tools and most HTTP tools open, or as JSON.

When a request names its event, the bin shows it as a badge. It reads the X-GitHub-Event, X-Gitlab-Event, X-Event-Key, X-Shopify-Topic, X-Webhook-Event and X-Event-Type headers, then the JSON fields type, event, event_type, eventType, topic and action.

Several bins

New bin creates another bin and keeps the ones you have. My bins lists every bin this browser created or opened with its private link, newest first, with its URL, where its requests go and how many it keeps. Click a name to rename it, Open to switch to it, or Remove to drop it from the list; the bin itself stays until it expires. The list lives in this browser only, so keep a bin's private link to open it elsewhere. A bin that has expired is removed from the list on its own.

Sharing a bin

Only the browser that created the bin holds its token. Share shows three links:

  • Webhook URL: the address webhooks go to. Anyone can send to it, but it shows nothing.
  • View-only link: opens the bin's requests and the answers they got, live, in any browser. It can't change rules, routing or the default answer, can't clear the bin and doesn't show the settings, so forward headers and the tunnel key stay private. Opening it doesn't replace the viewer's own bin; Leave goes back to it.
  • Private link: the token itself. Whoever has it controls the bin as you do; keep it to yourself.

From a script:

curl '…/__public/inspect/{id}?q=failed&method=POST&status=4xx' -H 'X-Bin-Token: {token}'
curl …/__public/inspect/{id}/requests/{seq} -H 'X-Bin-Token: {token}'
curl -X DELETE …/__public/inspect/{id}/requests/{seq} -H 'X-Bin-Token: {token}'
curl …/__public/inspect/{id}/requests/{seq}/share -H 'X-Bin-Token: {token}'
curl '…/__public/inspect/{id}/export?format=har' -H 'X-Bin-Token: {token}'

A request's share key, sent as X-Bin-Token, reads only /requests/{seq}. The owner reads the view key from viewKey in GET /__public/inspect/{id}/settings and a viewer sends it as X-Bin-Token to GET /__public/inspect/{id}. Every other call with it gets 403. A bin is deleted 24 hours after its last request.

Dynamic answers

Both the default answer and every rule answer can be built from each request. Dynamic value opens a searchable picker with the same groups as the stub editor: request components, control flow, data manipulation, validation, comparison, string, arithmetic, date and array helpers, JWT, random values, Faker and the bin's own state. Picking one inserts it and ticks Fill in dynamic values. You can also write template expressions yourself:

{
  "order": "{{jsonPath request.body '$.id'}}",
  "currency": "{{request.query.currency}}",
  "path": "{{request.path}}",
  "at": "{{now}}"
}

The picker leaves out what a bin can't run: datasets, the stub editor's state helper and hostname. A path variable is {{pathParams.id}}, filled from a rule's path pattern. A validation helper such as {{isEmail (jsonPath request.body '$.email') 'Enter a valid e-mail'}} refuses a bad request with 400 and {"error": "Enter a valid e-mail", "status": 400}, or with the status you give check.

Preview shows the answer built from the latest request the bin received, or from a sample request when there is none yet. Paths are the part under the bin, like /orders. The Dynamic answer starting point gives a rule that does this, with a new X-Request-Id header each time.

Saved state

A bin can remember things between requests, for a step counter, the last id it was sent or a list of everything it has seen:

ExpressionWhat it does
{{counter 'orders'}}Adds 1 and shows the new count: 1, 2, 3… add=5 or add=-1 changes the step, add=0 only reads, reset=true sets it to 0.
{{saveValue 'last-order' (jsonPath request.body '$.id')}}Saves a value and shows nothing.
{{savedValue 'last-order' default='none'}}Shows a saved value, or the default.
{{addToList 'orders' (jsonPath request.body '$.id')}}Adds to a list that keeps its newest 100 items, and shows nothing.
{{{savedList 'orders'}}}The list as JSON; use it with #each or len too.

A bin keeps up to 100 counters, values and lists, each value up to 4 KB and 64 KB in all. The state outlives restarts and goes when the bin does. Saved state at the bottom of Rules shows it, and Clear starts again. From a script, GET or DELETE /__public/inspect/{id}/state with the bin token.

Rules

Rules answer requests before routing does. The first enabled rule that matches answers; drag rules to change the order, untick one to skip it, or switch Rules on off to skip them all. A rule matches a method (any, GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS, QUERY or TRACE) and all of its conditions:

Look atName
Pathnone, the path under the bin, like /payments
Query parameterthe parameter
Headerthe header, any case
Body textnone
JSON fielda path like $.data.object.status or $.items[0].id
Form fielda field of an application/x-www-form-urlencoded body
XML fieldan XPath like //order/id; the body can't load DTDs or outside files
SOAP actionnone; read from the SOAPAction header or the action part of Content-Type
GraphQL operationnone; the operationName, else the named operation, else the first field of the query

Each condition tests the value with equals, doesn't equal, starts with, contains, doesn't contain, matches regex, is present or is absent. A missing value counts as not equal and not containing, so header X-Env doesn't equal prod also matches a request without the header.

The path can also match a pattern such as /users/:id or /orders/{orderId}/items. Each parameter matches one non-empty segment, and the answer reads it as {{pathParams.id}} when Fill in dynamic values is ticked.

A rule can have a description of up to 500 characters, shown under it in the list, so whoever opens the bin knows what it is for.

An answer has a status, a delay up to 15 seconds, headers and a body. The type picker beside Body sets Content-Type to JSON, XML, HTML, JavaScript, CSV or plain text; without one the bin guesses from the body. { } formats a JSON body. Tick Fill in dynamic values to render the body and headers as a template, for example {{jsonPath request.body '$.id'}}, {{now}} or {{fake 'Name.fullName'}}.

Send a file answers with a file of up to 16 KB, such as an image, a PDF or a CSV, byte for byte. Its type comes from the file, and the request log shows a binary answer as its size. A file has no dynamic values; Use text instead goes back to a text body.

Switch from One answer to Weighted answers to make a flaky endpoint. A rule has up to five answers, each with a weight, an optional description such as "Usually succeeds" and the share of requests it gets: weights 3 and 1 show 75% and 25%. Switching back keeps only the first answer.

The starting points fill the editor with a common rule: fail with 500, answer after 5 seconds, match one event type, echo the body back, fail one in four, accept then call back, and CRUD users. A bin holds up to 50 rules of up to 10 conditions each.

When the server has an AI provider, AI in the top bar, or Draft with AI under the rules, turns a description such as "answer 402 with the payment id when the event is payment.failed" into a rule. It needs a MockHub sign-in: anonymous visitors don't get AI drafts. Each user gets 10 drafts an hour. The draft opens in the editor and is saved only when you save it.

Callouts

A rule can also call another URL. Under Call out in the rule editor:

  • Call a URL, wait, and answer with its response: the bin sends the call, waits up to 15 seconds and passes the URL's status, headers and body back to the sender. The rule has no answer of its own. If the call fails or times out, the sender gets 502 with a JSON error and the request shows Callout failed.
  • Answer at once, then call a URL in the background: the sender gets the rule's answer straight away, and the call goes out after a random wait between the two times you set, up to 60 seconds. Use it for "accept now, call back later" flows such as payment or job webhooks.

The method is the request's own or one you pick. The call sends either the request's own body with its Content-Type, or a body written in the editor. The URL, the body and the headers can all use dynamic values, for example https://api.example.com/orders/{{pathParams.id}} or {"id": "{{jsonPath request.body '$.id'}}"}. Auth is none, a bearer token, Basic with a user and password, or a header of your own such as X-Api-Key; it is stored with the rule and is not shown in the log. Calls carry User-Agent: MockHub-Bin-Callout, don't follow redirects, read up to 1 MB and go only to public addresses.

Each request shows its callout under the answer: the method and URL without the query, the status and how long it took, or why it failed. A background callout shows sends 1.5 s after the answer until it goes out; the log picks up the result by itself, and the callout's response appears below it. A bin can have 20 background callouts waiting at a time. A background callout that is waiting when the server restarts is not sent, and the request says so.

From a script, a rule takes a callout:

{"name": "Accept, then call back", "method": "POST",
 "answers": [{"status": 202, "body": "{\"status\": \"accepted\"}"}],
 "callout": {"mode": "async", "method": "POST", "url": "https://example.com/callback",
             "payload": "custom", "body": "{\"id\": \"{{jsonPath request.body '$.id'}}\"}",
             "headers": {"X-Source": "bin"}, "auth": {"type": "bearer", "value": "…"},
             "minDelayMs": 1000, "maxDelayMs": 3000}}

mode is sync or async, method is same or a method, payload is original or custom, and auth.type is none, bearer (value), basic (name and value) or header (name and value). A sync callout needs no answers. Each request in GET /__public/inspect/{id} has a callout with state scheduled, sent or failed, plus status, millis, waitMs, error and, for background calls, the first 4 KB of the response.

CRUD routes

Pick CRUD route at the top of the rule editor to make the bin a small stateful API. Give it a collection path such as /users or /api/v1/orders, the id field (id by default) and how new ids are made: 1, 2, 3…, a UUID or a short id. The rule then answers:

RequestAnswer
GET /users200 with the records and X-Total-Count. Filter with ?role=admin, ?age[gte]=18 (ne, gt, gte, lt, lte), sort with _sort=name&_order=desc, page with limit and offset or page and size
POST /users201 with the record and Location; an id is added when the body has none, and 409 when the id is taken
GET /users/{id}200 with the record, or 404
PUT /users/{id}200 with the body as the new record; the id stays
PATCH /users/{id}200 with the fields merged in; a field set to null is removed
DELETE /users/{id}204, or 404

Other methods get 405, a body that isn't a JSON object gets 400, and errors are JSON with error and code. The route answers only its path and one level under it, so /users/7/orders and /users-archive go on to the next rule. The log shows these requests as CRUD. It is the same engine as the app's CRUD resources.

Records are kept with the bin, survive restarts and are deleted with it. A bin stores up to 500 records of up to 8 KB each, in up to 20 collections. Stored records in the Rules dialog shows each collection with its newest records; Clear empties one, Clear all empties them all. A view-only link can read them but not clear them.

From a script, a rule takes "crud": {"path": "/users", "idField": "id", "idType": "number"} and needs no answers; it can't also call out. GET /__public/inspect/{id}/data lists the stored collections. PUT …/data with {"route": {"path": "/users"}, "records": [{"name": "Ada"}]} replaces a collection with those records, and DELETE …/data, or …/data?collection=users, clears them.

Settings

Settings in the top bar changes how the bin treats every request, before rules and routing:

  • Answer CORS checks, on by default: a browser on any site can call the bin. A preflight gets 204 with the method and headers it asked for, and every answer has Access-Control-Allow-Origin: * and Access-Control-Expose-Headers: *. Turned off, a preflight is an ordinary OPTIONS request that rules and routing answer and the log keeps, and answers carry no CORS headers.
  • Require a header: a request without the header, or with another value, gets 401 and shows as Missing required header.
  • Rate limit: past a number of requests a second, minute or hour, the bin answers 429 with Retry-After and the log shows Rate limited. Requests refused for the header don't count.
  • Default latency: every answer waits this long, up to 15 seconds, unless its rule has a delay of its own.

The line beside the bin URL lists what is on, for example default answer (needs X-Api-Key · 10 a minute · +200 ms). From a script, PUT /__public/inspect/{id}/options with {"cors": true, "latencyMs": 200, "rateLimit": {"requests": 10, "per": "minute"}, "requiredHeader": {"name": "X-Api-Key", "value": "…"}} replaces them all; leave a setting out or set it to null to turn it off.

Routing

Routing decides what answers a request no rule matched.

  • Default answer: the bin's reply, 200 {"ok":true} unless you change it.
  • Forward: the request goes on to a target plus an optional path prefix plus the path under the bin, with its query, headers and body, and the target's answer goes back to the sender. You can add headers to every request and every answer, and skip TLS certificate checks. Only public addresses are allowed; the target has 15 seconds and 1 MB.
  • Local tunnel: the request reaches a service on your machine. Run the command the page shows, which uses the MockHub tunnel client with the bin's own key: 
    java -jar mockhub.jar tunnel --server https://mockhub.devops-monk.com \
  --token bin_{id}_{token} --name bin-{id} --to http://localhost:3000
    The bin's key opens only the tunnel named bin-{id}, and no other key can use a name that starts with bin-. The page shows whether the tunnel is connected.

When forwarding or the tunnel fails, the sender gets 502 with a JSON error, and the request shows Forward failed or Tunnel failed.

From a script

curl -X POST https://mockhub.devops-monk.com/__public/bins
curl https://mockhub.devops-monk.com/__public/inspect/{id} -H 'X-Bin-Token: {token}'
curl -X PUT https://mockhub.devops-monk.com/__public/inspect/{id}/rules -H 'X-Bin-Token: {token}' \
  -H 'Content-Type: application/json' -d '{"rulesEnabled": true, "rules": [{
    "name": "Failed payments", "method": "POST",
    "description": "Payment failures get 402",
    "conditions": [{"target": "json", "key": "$.type", "op": "equals", "value": "payment.failed"}],
    "answers": [{"status": 402, "delayMs": 500, "body": "{\"id\": \"{{jsonPath request.body '"'"'$.id'"'"'}}\"}", "template": true}]}]}'

An answer sends a file with "fileName": "logo.png" and the file's bytes in base64 as "body". Each answer can also have a "description" of up to 120 characters.

Every endpoint is listed under Public tools.
