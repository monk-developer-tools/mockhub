These numbers come from one run of the published Docker image on a laptop, measured with the load generator that ships with MockHub. Your hardware will give different numbers, so the last section shows how to repeat the run on your own machine.

How it was measured

PartSetting
MachineMacBook Pro, Apple M1 Pro (10 cores, 16 GB), Docker Desktop 20.10 with 5 CPUs and 4.8 GB for its VM. Other apps were running, so the host was not idle.
MockHubThe Docker image (135 MB), limited to 2 CPUs and 1 GB of memory, the size of a small cloud server. Default settings, so every request is also written to the request history on disk.
LoadA second container on the same Docker network, with 2 CPUs. Each connection is kept open and sends its next request as soon as the answer arrives. 20 seconds of warm-up, then 60 seconds measured per scenario.
LatencyMeasured from sending a request to reading the whole answer, for every request (no sampling).

With two CPUs the server is the limit: it stays at its CPU cap from 64 connections up, so more connections add waiting time, not throughput. Templating and JSON body matching cost little. Many stubs cost more, because WireMock checks stubs one after another until one matches; so give the stubs that get the most traffic a higher priority and they are checked first.

What the benchmark fixed

The first runs found four problems, which are fixed in this version:

  • Every request counted the whole request journal. WireMock counts the up to 5,000 requests it keeps in memory each time it serves one, to know when to drop the oldest. MockHub now keeps that journal itself and drops the oldest in constant time. Small answers went from about 8,400 to 47,000 requests per second on the same laptop without Docker.
  • Large responses ran the server out of memory. The journal kept 5,000 full response bodies, so 1 MB answers filled the heap in seconds. Bodies in the journal are now cut to 64 KB (MOCKHUB_JOURNAL_MAX_BODY_KB), and the journal drops its oldest requests once their bodies reach 64 MB (MOCKHUB_JOURNAL_MAX_MB).
  • History waiting to be written could fill the memory. When the disk fell behind, up to 20,000 entries waited in memory. The queue now holds at most 64 MB; past that, entries are left out of the history and counted.
  • History could grow far past its size cap. The 200 MB cap per project (MOCKHUB_HISTORY_MAX_MB) was checked every 30 minutes, and a busy hour went into a single file. One run wrote 16 GB. History now rolls into small files and keeps the cap while it writes: with a 20 MB cap, 4.9 million requests left exactly 20 MB on disk.

Repeat it on your machine

From a checkout of the repository, with Docker running:

./scripts/benchmark.sh

It builds the image and the load generator, runs every scenario and the 10-minute steady run, and writes results.md, results.json, server-stats.csv (memory and CPU every 5 seconds) and the server log to build/benchmark/<time>/. It takes about 25 minutes. Settings, as environment variables:

VariableDefaultWhat it changes
SERVER_CPUS, SERVER_MEMORY2, 1gLimits for the MockHub container
LOAD_CPUS2CPUs for the load generator
CONNECTIONS32Connections for every scenario except the connection sweep
WARMUP, DURATION, SOAK20, 60, 600Seconds of warm-up and measurement per scenario, and of the steady run (0 skips it)
ONLYallA comma-separated list of scenarios, such as hello-c64,payload-1mb,steady
SKIP_IMAGE_BUILDtrue reuses the image from the last run

To point the load generator at a server you already run, build it with ./gradlew shadowJar benchJar and run:

java -cp build/libs/mockhub.jar:build/libs/mockhub-bench.jar io.mockhub.bench.Benchmark \
  --base http://localhost:8080 --user admin --password '…' --duration 60 --soak 0

It signs in, creates a project called bench (replacing one with that name) and briefly a second one, bench-many. Don't run it against a server other people use.
