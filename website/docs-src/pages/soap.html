Choose SOAP stub, or switch an existing stub's service type to SOAP. Enter the operation element (the first element inside soap:Body, such as GetCustomer) and MockHub matches it for you. Add XPath conditions to answer differently per field value:

{ "matchesXPath": { "expression": "//*[local-name()='customerId']/text()", "equalTo": "42" } }

Import → WSDL creates, for the service's SOAP binding:

  • one stub per operation, with request and response envelopes generated from the XSD (including enums, attributes and nested types)
  • GET <endpoint>?wsdl, serving the WSDL with soap:address rewritten to the mock
  • a low-priority SOAP fault for operations without a mock

Without a WSDL

When you only have example requests, from a log, a partner's documentation or SoapUI, choose Import → SOAP samples and paste one or more envelopes. MockHub reads each one and finds:

  • the SOAP version, from the envelope namespace (1.1 or 1.2)
  • the operation, the first element inside soap:Body, and its namespace
  • the SOAPAction, from a SOAPAction header or the action parameter of a SOAP 1.2 content type, when the request came from the log

Each operation gets a stub that matches it and answers with an <Operation>Response envelope in the same namespace, ready to edit; the pasted request becomes its example. A last stub at priority 10 answers any other operation the same way and sends X-MockHub-Soap-Operation with the operation it found. A body that isn't a SOAP envelope gets a 400 SOAP fault. To answer unknown operations with a fault instead, set "transformerParameters": {"unknown": "fault"} on that stub.

The same detection works elsewhere: Create stub on a SOAP request in the Requests tab makes a SOAP stub with the right operation, version, SOAPAction and response envelope, and Fill operation from example in the editor reads them from the example request body.
