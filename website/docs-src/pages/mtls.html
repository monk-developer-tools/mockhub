MockHub can serve mocks over HTTPS with your own certificate, and accept client certificates (mutual TLS). A project can then refuse every caller that doesn't present a trusted certificate. Use this to test services that sign their calls with a certificate.

Turn on the HTTPS port

Set MOCKHUB_HTTPS_PORT and publish that port as well:

docker run -p 8080:8080 -p 8443:8443 -e MOCKHUB_HTTPS_PORT=8443 -v mockhub-data:/data abhaypratap/mockhub

Every project answers on both ports: http://host:8080/shop/… and https://host:8443/shop/…. At startup MockHub prints both addresses. Until you upload a certificate, HTTPS uses WireMock's built-in self-signed one, so clients have to skip verification (curl -k).

Your own server certificate

As an admin, open Server and paste the certificate and its private key under HTTPS and client certificates. You can also drop the .pem files there. Put the server certificate first, then any intermediates, then the unencrypted private key. MockHub reads PKCS#8 keys (BEGIN PRIVATE KEY, RSA, EC or EdDSA) and RSA keys in PKCS#1 (BEGIN RSA PRIVATE KEY). Convert anything else with openssl pkcs8 -topk8 -nocrypt -in key.pem.

MockHub checks that the key belongs to the certificate, then uses it for new connections straight away, with no restart. The key is stored encrypted in the data folder, with the same secret key as connections. Go back to the built-in certificate removes it.

Accept client certificates

Under Trusted client CAs, paste the certificates of the CAs that sign your callers' certificates. From then on MockHub asks every HTTPS caller for a certificate. A caller signed by one of those CAs is identified, and stubs see who it is in three request headers:

HeaderExample
X-MockHub-Client-Cert-SubjectO=Acme,CN=billing-service
X-MockHub-Client-Cert-IssuerCN=Acme Internal CA
X-MockHub-Client-Cert-Sha256The certificate's SHA-256 fingerprint in hex

Match on them like any header, for example to answer one service differently, or echo them with {{request.headers.X-MockHub-Client-Cert-Subject}}. MockHub removes these headers from every incoming request before it sets them, so a caller can't send them itself.

A caller without a certificate still connects, and so does one whose certificate no trusted CA signed. Both are treated as anonymous: no headers are set.

Require a certificate for a project

In a project's Settings → Runtime behaviour, turn on Client certificate. Calls without a trusted certificate then get:

HTTP/1.1 403 Forbidden
Content-Type: application/json

{"error":"This mock needs a client certificate. Call it over HTTPS with a certificate signed by a CA trusted on the Server page"}

Calls on the plain HTTP port can never carry a certificate, so they are refused too. gRPC calls arrive on the plain port, so they're refused with PERMISSION_DENIED. To try it with curl:

curl --cacert ca.pem --cert client.pem --key client.key https://localhost:8443/payments/whoami

Behind a load balancer

Client certificates only reach MockHub when the TLS connection ends at MockHub. A proxy or load balancer that terminates TLS itself, such as an AWS ALB or nginx with proxy_pass, drops them. Forward the HTTPS port as plain TCP instead (an AWS NLB with a TCP listener, or nginx's stream module), and keep the HTTP port behind your usual proxy.
