• Fixed: always wait N ms.
  • Random range: uniform between two values.
  • Realistic: log-normal latency around a median, with a long tail.
  • Trickle: send the body in chunks over a period of time.
  • Faults: connection reset, empty response, malformed chunk, or random data then close.

Latency for a whole project

To slow every answer of a project down, without touching each stub, pick a delay in Settings → Runtime behaviour → Latency: Fixed, Random range or Realistic (log-normal around a typical delay, with a spread from 0.1 for steady to 1 for very spiky). Delays go up to 60 seconds. Stubs that set their own delay keep it.

Get slower under load adds time when the project gets busy, like a real service near capacity: above a number of requests a second, each extra request adds some milliseconds, up to 30 seconds. For example, above 10 requests a second with 20 ms each, a project getting 25 requests a second adds 300 ms to every answer. Use it in load tests to see how your timeouts and retries behave.

A global delay for every project on the server is on the Server page.

Random failures. Under Failures, make a share of calls fail, for example 10%, with an error status or a network fault. The rest get the normal response. Failed calls carry X-MockHub-Simulated-Error: true. Without a body of your own, REST stubs answer {"error":"Simulated failure"} and SOAP stubs answer a SOAP fault. In JSON, it's stored on the stub as:

"metadata": { "mockhub": { "errorRate": { "percent": 10, "status": 503 } } }
