MockHub documentation

Everything you need to run MockHub, mock REST and SOAP services, share them with your team, and run it in production test environments.

New to MockHub? The step-by-step tutorials walk through every feature with screenshots.

Quick start

docker run -p 8080:8080 -v mockhub-data:/data abhaypratap/mockhub

Open http://localhost:8080/__admin/mockhub/ui/. Go to Examples, install Petstore — REST basics, then call it. Ten examples cover every feature; the tour of the examples walks through them.

curl http://localhost:8080/example-petstore/pets/42
{"id":"42","name":"Pet 42","status":"available"}

Want to look around first? The live demo runs the examples. Sign in as demo / demo (read-only), and call the mocks directly:

curl https://mockhub.devops-monk.com/example-petstore/pets?status=sold

Concepts

TermMeaning
ProjectThe mocks of one service. It owns a base path such as /payment-service, so its mock URL is https://your-host/payment-service.
Root projectAt most one project per server can answer at the root: its stubs match without a base path, exactly like a plain WireMock server. Paths that start with another project's base path still go to that project.
StubA rule: when a request matches, send this response. Stubs are plain WireMock stub mappings, edited relative to the project's base path.
PriorityWhen several stubs match, the lowest number wins (1 is highest, the default is 5). Use it for "specific case first, generic fallback last".
ScenarioA named state machine that lets the same request get different answers over time.

Your first stub

Create a project, open it, and choose REST stub. Set the method and path, then the response status and body, and save. Click Send in the Try it panel to call it.

The form covers the common cases. Switch to JSON for anything else WireMock supports. This is the same stub as JSON, as sent through the API:

{
  "name": "Get payment",
  "request": { "method": "GET", "urlPathTemplate": "/payments/{id}" },
  "response": {
    "status": 200,
    "headers": { "Content-Type": "application/json" },
    "jsonBody": { "id": "{{request.path.id}}", "status": "PAID" },
    "transformers": ["response-template"]
  }
}

Not sure where to start? The template gallery button in the stub list has ready-made patterns for common cases.

Under Call it from your code, every stub has a snippet you can copy as cURL, HTTPie, JavaScript, Python, Java, C# or Apex. The request log offers the same for any request it captured.

Request matching

URL matchExampleMatches
Path equals/pets/pets, /pets?any=query
Path and query equal/pets?status=soldexactly that URL
Path template/pets/{id}/pets/7, and exposes request.path.id
Path matches regex/pets/[0-9]+numeric ids only
Any URLanything under the project's base path

Add conditions on query parameters, headers, cookies and the body. Every condition must match. Body matchers include JSON equals (optionally ignoring extra fields and array order), JSONPath (for example $[?(@.amount > 1000)]), XML equals, XPath, contains and regex.

The patterns teams use most, like magic test ids for error paths, a regex on one body field with a low-priority fallback, filters inside arrays, one stub for every environment and proxying chosen ids to a real service, are explained step by step in Matching patterns from real projects and installed together as the Matching patterns example.

Templating

Turn on Response templating to build responses from the request:

HelperGives
{{request.path.id}}a path-template variable
{{request.query.page}}a query parameter
{{request.headers.X-Tenant}}a header
{{jsonPath request.body '$.email'}}a value from a JSON body
{{xPath request.body '//id/text()'}}a value from an XML/SOAP body
{{randomValue type='UUID'}}a random UUID (also ALPHANUMERIC, NUMERIC…)
{{randomInt lower=1 upper=100}}a random number
{{now offset='7 days' format='yyyy-MM-dd'}}dates
{{#if …}} {{#eq a 'b'}} {{#each …}}conditionals and loops

See the WireMock templating reference for the full list.

Fake data

Templated responses can use {{fake '…'}} with any Datafaker expression. In the editor, Fake data lists the common ones.

WriteGives
{{fake 'Name.fullName'}}a person's name
{{fake 'Internet.emailAddress'}}an e-mail address
{{fake 'Address.city'}}, {{fake 'Address.streetAddress'}}places
{{fake 'Company.name'}}, {{fake 'Commerce.productName'}}business data
{{fake 'Number.numberBetween' 1 100}}a number in a range
{{fake 'Name.fullName' locale='de'}}another language

The default language comes from MOCKHUB_FAKE_LOCALE (en). Importing an OpenAPI spec also fills fields by name and format (e-mail, phone, city, dates, prices) with realistic values that stay the same on every import.

Data generator

Generate data in the stub editor builds a fixed JSON list: choose fields (ids, names, e-mails, addresses, prices, IBANs, any Datafaker expression), up to 1,000 records, a language and an optional key to wrap the list in. Dots in a field name nest it, e.g. address.city. The CRUD resource dialog uses the same generator for starting records. Over the API:

curl -X POST $HUB/__admin/mockhub/api/fake/generate \
  -d '{"count":3,"fields":[{"name":"id","expression":"sequence"},{"name":"email","expression":"Internet.emailAddress"}]}'

CRUD resources

In Stubs, choose CRUD resource and name it, e.g. customers. MockHub creates one stub that handles:

RequestDoes
GET /customerslist; filter with ?city=London, sort with _sort=name&_order=desc, page with _limit and _offset; the total is in X-Total-Count
GET /customers/{id}one record, or 404
POST /customerscreate; the id is generated (1, 2, 3 or a UUID) unless you send one; 201 with a Location header
PUT /customers/{id}replace
PATCH /customers/{id}merge fields; null removes one
DELETE /customers/{id}delete; 204

Records are kept per project in /data/mockhub/data, survive restarts and are included in backups. The Data tab lists them and lets you add, edit, delete or clear them. For custom stateful flows, the WireMock state extension is included too (its state lives in memory).

Scenarios

Give stubs the same scenario name. Each stub answers only in its required state and can move the scenario to a new state. Every scenario starts in Started. Reset or jump between states from the project's Scenarios tab. The Shopping cart example shows a complete flow.

Webhooks

In the editor's Then call section, add one or more webhooks: method, URL, headers, body and an optional delay. They are sent after the stub answers. Use {{originalRequest.body}}, {{jsonPath originalRequest.body '$.id'}} or {{originalRequest.headers.X-Id}} to pass data from the request. They're stored as standard WireMock serveEventListeners, so existing WireMock webhook mappings work unchanged.

Response files

On Import & export, upload files up to 10 MB under Response files: PDFs, images, large JSON. In a stub, choose File as the body type and pick the file; the Content-Type is set for you. Files are kept per project, removed with the project, and included in backups.

Delays & faults

  • Fixed: always wait N ms.
  • Random range: uniform between two values.
  • Realistic: log-normal latency around a median, with a long tail.
  • Trickle: send the body in chunks over a period of time.
  • Faults: connection reset, empty response, malformed chunk, or random data then close.

A global delay for every response is on the Server page.

Random failures. Under Failures, make a share of calls fail, for example 10%, with an error status or a network fault. The rest get the normal response. Failed calls carry X-MockHub-Simulated-Error: true. Without a body of your own, REST stubs answer {"error":"Simulated failure"} and SOAP stubs answer a SOAP fault. In JSON, it's stored on the stub as:

"metadata": { "mockhub": { "errorRate": { "percent": 10, "status": 503 } } }

API keys

In a project's Settings, turn on Require an API key and choose the header (default X-API-Key) and the key. Every call under the project's base path must then send it. Calls without the right key get a 401: JSON for REST, a SOAP 1.1 or 1.2 fault for SOAP. OPTIONS preflights and ?wsdl stay open. Only admins can see, set or change the key. For admins, Try it, code snippets and the Postman and Bruno exports send the key automatically; everyone else sees X-API-Key · set and gets a {{apiKey}} placeholder to fill in with the key an admin shares.

On, off & usage

Flip the switch at the top of a stub to turn it off. Requests then skip it as if it were deleted, but it stays saved, in exports and in backups. The number next to each stub in the list, and the line under the switch, show how many calls it answered and when, counted from the request log. Clearing the log or restarting resets the counts.

SOAP & WSDL

Choose SOAP stub, or switch an existing stub's service type to SOAP. Enter the operation element (the first element inside soap:Body, such as GetCustomer) and MockHub matches it for you. Add XPath conditions to answer differently per field value:

{ "matchesXPath": { "expression": "//*[local-name()='customerId']/text()", "equalTo": "42" } }

Import → WSDL creates, for the service's SOAP binding:

  • one stub per operation, with request and response envelopes generated from the XSD (including enums, attributes and nested types)
  • GET <endpoint>?wsdl, serving the WSDL with soap:address rewritten to the mock
  • a low-priority SOAP fault for operations without a mock

Proxy & record

Set a stub's response to Proxy to forward matching requests to a real service. A low-priority "any URL" proxy stub lets you mock a few endpoints and pass everything else through. The project's base path is removed before forwarding.

Server → Record from a real service forwards traffic to a target and saves every answer as a stub in the project you choose.

Moving from WireMock

  1. Zip the folder that holds mappings and __files, for example src/test/resources/wiremock.
  2. Create a project and import the zip under Import & export → WireMock folder.
  3. In the project's Settings, turn on Answer at the root. URLs, and templates that count path segments such as {{request.pathSegments.[0]}}, then behave exactly as before.
  4. Point your services at MockHub instead of the old WireMock host.

Stubs that relied on templating switched on for every stub need "transformers": ["response-template"], or start MockHub with WIREMOCK_OPTIONS=--global-response-templating. Runtime calls to /__admin/mappings keep working with a MockHub token. Step by step: Move from WireMock.

Postman & Bruno

On a project's Import & export tab:

  • Postman: a v2.1 collection grouped into folders, with a baseUrl variable and a status test per request. Import it from Postman's Import dialog.
  • Bruno: a zip containing a collection folder of .bru files and a MockHub environment. Unzip it and use Open Collection.
  • WireMock: plain mappings for any WireMock server.

Request bodies come from each stub's matchers, or from the Example request body you set in the editor. Change baseUrl to run the same collection against the real service.

Request log

The Requests tab updates live. Filter to Unmatched to find missing stubs. Click a request to see headers and bodies, the closest stubs and how near they came, a button that creates a stub from that request, and Replay in Playground.

Playground

The Playground (sidebar) sends requests to your mocks or to public APIs from the server, so browser CORS rules don't get in the way. It shows status, time, size, headers and a formatted body, and can copy the request as cURL or save the response as a stub in any project you can edit. It needs the editor role.

  • History: your last 100 requests and responses, private to you. Values of Authorization, Proxy-Authorization, Cookie and Set-Cookie are hidden before saving, and bodies over 64 KB are cut short.
  • Own mocks: paths like /shop/orders and URLs on MockHub's own address go straight to the local mocks. /__admin is refused.
  • Safety: private, loopback, link-local and other internal addresses are refused so the server can't be used to reach your network. Set MOCKHUB_PLAYGROUND_ALLOW_PRIVATE=true to allow them, for example to call services on your intranet. Redirects aren't followed; responses over 2 MB are cut short; requests time out after 30 seconds.

Organisations, teams & roles

Sign-in is off until the first user exists. Open Users and create an admin, or start with a break-glass account in MOCKHUB_USERS. Mock endpoints are never protected; only the UI and the admin API are.

MOCKHUB_USERS="root:change-me:admin"

An organisation is your company or department. It holds teams, and each team owns its projects. Add people under Teams & people → Add people in three choices: who, where (the whole organisation or only some teams) and what they can do. Pick an organisation with the switcher at the top of the sidebar. Teams live inside an organisation and own its projects. Every organisation has a General team, and projects from before teams existed move there. People get a role in single teams, an organisation-wide role that applies to every team, or both; the higher role wins, and team members only see their own teams' projects. Moving a project to another team or organisation doesn't change its mock URL. See the teams tutorial for a walk-through.

RoleIn a teamOrganisation-wide
viewersee the team's projects, stubs and request logs, and download exportsthe same, in every team
editoralso add, change and delete stubs, import, record, and edit data and scenariosthe same, in every team
manageralso create, rename, move and delete projects, and manage the team's membersalso create and delete teams, manage members and the organisation
admina server role: everything, plus creating organisations and seeing or changing every secret

Only members see a team's projects. Someone in the Checkout team can't open, change or delete the Search team's projects, stubs, request log or activity, and the admin API answers 403. Mock URLs are different: apps and tests call them without signing in, so turn on an API key when a project's mocks must stay private.

Secrets stay with admins. Only admins create organisations, see or change a project's API key, and configure the AI assistant, single sign-on and backups. Managers and editors see X-API-Key · set; Try it, code snippets and Postman / Bruno exports use a {{apiKey}} placeholder, which Postman and Bruno mark as a secret variable to fill in. Existing owner memberships and SSO mappings become manager automatically.

Audit log

MockHub records every change: who created, changed, turned off or deleted a project, stub, team, person or setting, and when. A deleted stub keeps the name it had, so you can still tell what was removed. Open a project's Activity tab to see its history. Admins see every change under Audit log; organisation and team managers see the changes in what they own. Each entry shows the exact time to the second in your time zone, plus how long ago. Select an entry for the full date, the UTC timestamp, who did it and the entry ID. Filter by created, changed or deleted, by person and by the last 24 hours, 7 days or 30 days, and download what you see as CSV. Failed attempts, such as a refused delete, aren't recorded.

Entries are kept for 90 days, then removed from disk to save space. Change this with MOCKHUB_AUDIT_RETENTION_DAYS. Each entry is also printed to standard output as one line, so your log platform keeps its own copy:

2026-03-10T09:14:02.511Z INFO audit - Sam Patel: Deleted stub “GET /orders” {"actor":"Sam Patel","action":"deleted","target":"stub",...}

Each user also has a server role. Viewer everywhere and editor everywhere apply to every organisation. Admin also manages users, single sign-on, backups and the native WireMock API. Changing a password or disabling a user signs out that user's other sessions.

Single sign-on with Microsoft Entra ID

  1. In the Entra admin centre, open App registrations → New registration. Choose Web and paste the redirect URI shown under MockHub → Single sign-on: https://<host>/__admin/mockhub/api/auth/sso/azure/callback.
  2. Copy the Application (client) ID and Directory (tenant) ID. Under Certificates & secrets, create a client secret and copy its value.
  3. Optional: add a groups claim under Token configuration, or define App roles.
  4. Paste the values into MockHub and choose Test connection. Then set the allowed domains, the organisation and role every new user gets, and mappings from group IDs or app roles to roles. Turn it on and save.

MockHub uses the authorisation code flow with PKCE and checks the ID token's signature, issuer, audience, expiry and nonce. Roles from groups are refreshed at every sign-in; roles set by hand are kept. Set MOCKHUB_PUBLIC_URL behind a proxy so the redirect URI matches. Supply the secret with MOCKHUB_SSO_CLIENT_SECRET if you keep it in a secret store.

In a project, open Assistant and describe what you need, or paste an OpenAPI spec, a WSDL or curl commands. The assistant reads the stubs and recent requests and stages changes. API & CI

Everything in the UI is available over HTTP at /__admin/mockhub/api. With sign-in on, send HTTP Basic credentials. The native WireMock API stays available at /__admin.

# create a project
curl -X POST $HUB/__admin/mockhub/api/projects -d '{"name":"Orders","slug":"orders"}'

# load stubs from your OpenAPI spec before the test run
curl -X POST $HUB/__admin/mockhub/api/projects/$ID/import/openapi --data-binary @openapi.yaml

# add one stub (paths are relative to the project)
curl -X POST $HUB/__admin/mockhub/api/projects/$ID/stubs \
  -d '{"request":{"method":"GET","url":"/health"},"response":{"status":200}}'

# download the Postman collection
curl -OJ $HUB/__admin/mockhub/api/projects/$ID/export/postman

# require an API key on every mock call (null turns it off)
curl -X PUT $HUB/__admin/mockhub/api/projects/$ID -d '{"apiKey":{"header":"X-API-Key","value":"test-key"}}'

# check which calls your service made, and which didn't match
curl "$HUB/__admin/mockhub/api/projects/$ID/requests?unmatched=true"

  mockhub-data:

AWS ECS with Terraform

The repository's deploy/terraform module creates a Fargate service, an encrypted EFS volume for /data, an Application Load Balancer with optional HTTPS, and the IAM and security groups around them.

cd deploy/terraform
cp terraform.tfvars.example terraform.tfvars
terraform init && terraform apply

Running on a platform you already have, such as ECS with your own Terraform modules? Point the load balancer health check at /__admin/health, give /data a persistent volume (EFS on Fargate), and run one task: MockHub keeps its data in files, so scale up rather than out. To attach an APM agent, mount it and add -javaagent:/path/agent.jar to JAVA_TOOL_OPTIONS.

Logs

MockHub writes all of its logs to standard output, one line per event with a UTC timestamp, so the awslogs driver on Fargate sends them to CloudWatch with nothing to set up (the Terraform module already does this). You'll see:

  • startup, with the port, data folder and how sign-in works
  • every change from the audit log, as INFO audit
  • sign-ins, failed sign-ins (WARN) and refused requests with the reason
  • errors with their stack trace (ERROR)

To log every mock request too, add --verbose to WIREMOCK_OPTIONS. In CloudWatch Logs Insights, find who deleted something with:

fields @timestamp, @message
| filter @message like /INFO audit/ and @message like /Deleted/
| sort @timestamp desc

Persistence & backup

Stubs live in /data/mappings as WireMock JSON files. Projects live in /data/mockhub/projects.json, and response files in /data/__files. Back up the volume, or use Administration → Backup & restore.

There you tick whole organisations, single projects or a mix, and download them with their stubs as one JSON file. Users and sign-in settings are never included. To restore, open a backup file: MockHub lists what's inside and what each project would do here (new, replaces an existing project, or moves to a free base path). Pick the projects you want, the organisation to put them in, and whether existing projects are replaced or kept with a copy added beside them. The file restores into any MockHub.

Limits

  • Run one instance per data directory. WireMock keeps stubs in memory and reads the files only at startup.
  • Scenario states and the request log are in memory and reset on restart.
  • Project base paths can't collide with each other or with /__admin.
