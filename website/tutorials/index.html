The basics10 minNeeds the editor role

Tour of the examples

The quickest way to learn MockHub is to install the examples and call them. Each one is a normal project, so you can open every stub, read the note that says what it shows, change it and see what happens. Together they cover every feature.

  1. Install an example

    Open Examples in the sidebar and select Install as project on a card. MockHub creates a project with the example's stubs in your team. Open Stubs: each stub has a short note saying what it shows. The commands below use your server's address; set it once:

    MOCK=https://mockhub.example.com

  2. Petstore: how matching works

    The same URL can give different answers. A query, a header or a field in the body decides which stub wins, and priority breaks ties (1 is checked first).

    curl $MOCK/example-petstore/pets               # every pet
curl "$MOCK/example-petstore/pets?status=sold"  # query matcher wins
curl $MOCK/example-petstore/pets/999            # 404 beats the template
curl -X DELETE $MOCK/example-petstore/pets/1    # 401 without a token

    Now call a URL that doesn't exist, like /example-petstore/owners, and open the project's Requests tab. Unmatched calls are marked, with the closest stub and why it missed.

  3. Fake data: realistic, different every time

    Call the same URL twice and get a new person each time. The id still comes from the URL.

    curl $MOCK/example-fake-data/customers/C-1001
curl $MOCK/example-fake-data/customers           # five rows from a loop
curl $MOCK/example-fake-data/de/customers/random # German names and streets
curl $MOCK/example-fake-data/orders/A-1          # delivery date is always 3 days ahead

    Open a stub and look at its body: {{fake 'Name.fullName'}}, {{now offset='3 days'}}. In the editor, Fake data lists what you can use.

  4. Dynamic responses: answers built from the request

    curl "$MOCK/example-templating/echo/anything?q=hello" -H "X-Trace: 42"
curl -X POST $MOCK/example-templating/quotes \
  -d '{"sku":"A-1","quantity":12,"tags":["gift","express"]}'
curl "$MOCK/example-templating/greeting?name=Ana" -H "Accept-Language: de"

    The quote reads fields from the body, loops over the tags and picks a tier with a condition. See Dynamic responses for the helpers.

  5. Matching patterns: what real projects use

    Magic test ids that always fail, regular expressions and JSONPath filters on body fields, a fallback for everything else, one stub for every environment, and content negotiation.

    curl -X POST $MOCK/example-patterns/shipping/v1/labels \
  -d '{"orderId":"ORDER-404","returnUrl":"https://shop.example.com/r"}'   # 404
curl $MOCK/example-patterns/catalog/test/v1/products/BOOK-42
curl $MOCK/example-patterns/reports/v1/daily -H "Accept: text/csv"

    The matching patterns tutorial explains each one.

  6. Orders: a REST API that remembers

    One CRUD stub handles the whole resource. What you POST is saved, so the next GET returns it, even after a restart.

    curl "$MOCK/example-orders/orders?city=London"
curl -X POST $MOCK/example-orders/orders -d '{"customer":"Ana Silva","total":12}'
curl -X PATCH $MOCK/example-orders/orders/4 -d '{"status":"SHIPPED"}'
curl -X DELETE $MOCK/example-orders/orders/1
curl $MOCK/example-orders/orders/summary         # a normal stub beside the CRUD one

    Open the project's Data tab to see, edit or clear the saved orders.

  7. Shopping cart: answers that change over time

    curl $MOCK/example-cart/cart                     # empty
curl -X POST $MOCK/example-cart/cart/items -d '{"sku":"A-1"}'
curl $MOCK/example-cart/cart                     # now holds the item
curl -X POST $MOCK/example-cart/cart/checkout

    Open Scenarios to see the current state and reset it to start again.

  8. Payments: webhooks

    Like a real payment provider, the mock answers PENDING straight away and calls you back later. Point the callback at the example's own receiver to watch it arrive:

    curl -X POST $MOCK/example-webhooks/payments -d '{"reference":"ORDER-7","amount":25,
  "callbackUrl":"'$MOCK'/example-webhooks/partner/callbacks"}'
curl -X POST $MOCK/example-webhooks/payments -d '{"reference":"ORDER-8","amount":5000,
  "callbackUrl":"'$MOCK'/example-webhooks/partner/callbacks"}'

    Two seconds later the Callouts tab shows each callback with the body sent and the answer, and the Requests tab shows them arriving: SETTLED for the first and DECLINED for the large amount. In your own tests, use your service's callback URL instead.

    Two more stubs show the other modes. The refund is forwarded to the partner as is, and the card check waits for the issuer and answers with the issuer's response:

    curl -X POST $MOCK/example-webhooks/refunds -d '{"reference":"ORDER-7","amount":25}'
curl -X POST $MOCK/example-webhooks/cards/check -d '{"card":"4242424242424242"}'   # 201 from the issuer
curl -X POST $MOCK/example-webhooks/anything -d '{"event":"ping"}'                 # caught: 200

  9. Resilience: slow, failing and switched-off services

    curl -m 2 $MOCK/example-chaos/slow              # times out: it waits 3 s
curl $MOCK/example-chaos/flaky; curl $MOCK/example-chaos/flaky   # 503, then 200
for i in $(seq 10); do curl -s -o /dev/null -w "%{http_code} " $MOCK/example-chaos/unreliable; done

    About one call in five fails. Then open Stubs, turn on Maintenance page — switched off and call any URL: everything answers 503 until you turn it off again. The Calls column shows how often each stub was used.

  10. Bookshop: from an OpenAPI file, with response files

    The stubs were generated from an OpenAPI spec, then an error case was added by hand. Two stubs send files instead of a typed body.

    curl $MOCK/example-bookshop/books
curl $MOCK/example-bookshop/books/000            # hand-written 404
curl $MOCK/example-bookshop/price-list.csv       # a response file

    Open Import & export → Response files to replace the CSV or upload your own, and /covers/123 in a browser for the image.

  11. Calculator: SOAP

    curl "$MOCK/example-soap/ws/calculator?wsdl"
curl -X POST $MOCK/example-soap/ws/calculator -H "Content-Type: text/xml" -d \
  '<s:Envelope xmlns:s="http://schemas.xmlsoap.org/soap/envelope/"><s:Body>
   <c:Add xmlns:c="http://example.com/calculator"><c:a>2</c:a><c:b>3</c:b></c:Add>
   </s:Body></s:Envelope>'

    One stub per operation came from the WSDL. A hand-written stub matches on the values inside the envelope with XPath and returns a SOAP fault for negative numbers.

Make it yours. Change a stub and select Try it in the editor to see the new answer. Download any example as a Postman or Bruno collection from Import & export. Delete the project from its Settings when you're done.

Next: Create your first project

The basics2 minNeeds the editor role

Create your first project

A project holds the mocks for one service, like a payments API, and gives it its own base URL. Your app calls that URL instead of the real service.

  1. Select New project

    On the Projects page, select New project at the top right.

  2. Name it after the service you're replacing

    Type a name like Billing API. MockHub suggests a base path from it, and every mock in the project lives under that path. Add a description if you like, then select Create project.

    Tip. If the AI assistant is on, describe the API in Describe the API and it drafts the stubs for you. See the AI tutorial.

  3. Point your app at the mock URL

    The project opens on Overview. Under Connect your app, pick how your app is configured (environment variable, Spring, Docker Compose or cURL) and copy the line into your test setup in place of the real service's URL.

Good to know. Calling a mock never needs a password. Signing in is only needed to change mocks.

Next: Add your first stub

The basics4 min

Add your first stub

A stub is one rule: when a request looks like this, answer with that. Here you'll make GET /payments/{id} return a payment.

  1. Open Stubs and choose REST stub

    In your project, open the Stubs tab and select REST stub. From a template starts from common patterns, and Import brings in specs you already have.

  2. Describe the request to match

    Pick the method, then how to match the URL: an exact path, a path template like /payments/{id}, or a pattern. Paths are relative to the project's base path, and the full URL shows underneath. Add query parameters, headers, cookies or body rules only if your request needs them.

  3. Write the response and save

    Set the status, headers and body. The body can be JSON, XML, text or a file. Select Save, or press ⌘S. The stub answers straight away.

When two stubs match, the one with the lower priority number wins. Give special cases like /payments/0 priority 1 so they win over the general rule.

Next: Test a stub in the editor

The basics2 min

Test a stub in the editor

You don't need a terminal to check a stub. Try it sends a real request to the project's mock URL and shows you what came back.

  1. Scroll to Try it and select Send

    At the bottom of the editor, the method and path are filled in from the stub. Replace placeholders with real values, like /payments/7, add headers or a body if needed, and select Send. You'll see the status, the time it took and the response.

Save first. Try it calls the live mock, so save your latest changes before testing them. Below Try it, Call it from your code gives the same request as cURL, HTTPie, JavaScript, Python, Java, C# or Apex.

Next: Call any API in the Playground

The basics3 minNeeds the editor role

Call any API in the Playground

The Playground sends requests to your mocks or to any public API and shows the full response. Every request is kept in your history, and any response can become a stub.

  1. Send a request

    Open Playground in the sidebar. Pick a method, then type a URL: start typing to pick one of your projects, use a path such as /shop/orders, or paste a public address like https://api.example.com/users. Add query parameters, headers and a body in the tabs, and select Send. The response shows the status, time, size, body and headers.

  2. Go back to anything you sent

    History keeps your last 100 requests with their responses. Filter by URL, method or status, select one to load it again, or delete what you don't need. Passwords and tokens in Authorization and Cookie headers are hidden before anything is saved.

  3. Turn a response into a stub

    Select Save as stub. Choose the project and check the path, and MockHub creates a stub that returns the same status, content type and body. It's the fastest way to copy a real API's answers.

  4. Replay a request from the log

    In a project's Requests tab, select a request and choose Replay in Playground. It opens with the same method, path, headers and body, ready to change and send again.

Private addresses are blocked. So the server can't be used to reach your internal network, the Playground won't call private or local addresses such as 10.x, 192.168.x or localhost, except MockHub's own mocks. An admin can allow them with MOCKHUB_PLAYGROUND_ALLOW_PRIVATE=true.

Next: Search requests and fix the misses

The basics4 min

Search requests and fix the misses

Every call to a project is kept for days. See how much traffic arrives, find any call by what it sent, and turn the ones that found no stub into stubs.

  1. Watch the traffic

    Open the Requests tab. The chart counts calls over the last 5 minutes up to 24 hours, with unmatched calls in amber, and shows the average and peak requests per second. Choose 30d to see one bar per day. Hover a bar for its numbers, or drag across a spike to list just those requests.

  2. Find the calls you care about

    Type any text from the URL, headers or body, or filter by method, status (404 or 4xx), stub, header (X-Tenant:acme) and time. The chips count results by status: click 4xx or unmatched to filter by it. The filters live in the page address, so you can share the search. Export HAR downloads what matches.

  3. Open an unmatched call and create its stub

    Select a request. For one that found no stub, the panel lists the closest stubs and how near each came, so you can spot a typo in a path or a missing header. Select Create stub from this request to start a stub that's already filled in, or Replay in Playground to send it again.

Ask the assistant. It searches the same history, so you can ask "Which calls found no stub in the last hour?" and let it stage the missing stubs. History is kept for 7 days by default; see Request history to change that.

Next: Turn stubs off and see what's used

The basics2 min

Turn stubs off and see what's used

Pause a stub without deleting it, and see which stubs your app actually calls.

  1. Turn a stub off

    Open a stub and flip the switch at the top to Off. Requests then skip it, as if it were deleted, so a more general stub or a 404 answers instead. Everything about the stub is kept. Flip it back On when you need it again.

  2. See how often each stub is called

    The number next to each stub in the list is how many calls it answered, counted from the request log. The editor shows the count and when it was last called. Stubs without a number haven't been called yet.

Counts follow the request log. Clearing the log or restarting the server resets them. The log keeps the latest 5,000 requests by default (MOCKHUB_JOURNAL_MAX_ENTRIES).

Next: Matching patterns from real projects

Realistic mocks6 min

Matching patterns from real projects

The same handful of patterns turns up in almost every WireMock setup that teams use for years. Install Matching patterns — from real projects from Examples and follow along: every stub there shows one pattern, with an example request ready in Try it.

  1. Magic test ids for error paths

    Testers need to reach the error paths on purpose. Pick ids that always fail, and match them in the body with a JSONPath filter. Give these stubs Priority 1 so they win over the normal answer.

    {
  "priority": 1,
  "request": {
    "method": "POST",
    "urlPath": "/shipping/v1/labels",
    "bodyPatterns": [{ "matchesJsonPath": "$[?(@.orderId == 'ORDER-404')]" }]
  },
  "response": { "status": 404, "jsonBody": { "errors": [{ "code": "ORDER_NOT_FOUND" }] } }
}

    Write the ids down in the stub's Description, so everyone knows that ORDER-404 returns 404 and ORDER-503 returns 503.

  2. A regex on one field, then a fallback

    Check a single field with expression and matches. Anything that doesn't match falls through to a lower-priority stub that returns the validation error.

    { "priority": 3, "request": { "method": "POST", "urlPath": "/shipping/v1/labels",
    "bodyPatterns": [{ "matchesJsonPath": {
      "expression": "$.returnUrl", "matches": "^https://shop\\.example\\.com/.*" } }] },
  "response": { "status": 201 } }

{ "priority": 4, "request": { "method": "POST", "urlPath": "/shipping/v1/labels" },
  "response": { "status": 422, "jsonBody": { "errors": [{ "code": "INVALID_RETURN_URL" }] } } }

    Lower numbers win. Priority 1 beats 3, which beats 4. Leave gaps so you can slot a stub in later without renumbering.

  3. Look inside arrays

    A filter in square brackets matches when any item fits. Here, a basket that contains a gift card gets free shipping:

    { "matchesJsonPath": "$.items[?(@.sku == 'GIFT-CARD')]" }

  4. One stub for every environment

    Paths often carry an environment or version, like /catalog/test/v1/products/BOOK-42. Use a path template and read the parts by name:

    { "request": { "method": "GET", "urlPathTemplate": "/catalog/{environment}/v1/products/{sku}" },
  "response": { "transformers": ["response-template"],
    "body": "{ \"environment\": \"{{request.path.environment}}\", \"sku\": \"{{request.path.sku}}\" }" } }

    Counting segments? {{request.pathSegments.[4]}} counts from the start of the whole path, and that includes the project's base path. Named variables don't care where the project lives. If you're moving mappings that count segments, turn on Answer at the root and they keep working unchanged.

  5. Send chosen ids to the real service

    Keep a few real test accounts working end to end and mock everyone else. The proxy stub matches only the chosen id at priority 1; a priority 5 stub answers any other well-formed id.

    { "priority": 1, "request": { "method": "POST", "urlPath": "/customers/v1/lookup",
    "bodyPatterns": [{ "matchesJsonPath": "$[?(@.customerId == 'C1000001')]" }] },
  "response": { "proxyBaseUrl": "https://test-api.example.com" } }

    In the example the proxy stub is switched off. Change proxyBaseUrl to your test environment and turn it on.

  6. Fixed values with transformer parameters

    Keep values out of the body file and in the stub, then read them with {{parameters.name}}. One body file can then serve several stubs with different values.

    "response": {
  "transformers": ["response-template"],
  "transformerParameters": { "title": "Ms", "lastName": "Rivera" },
  "body": "{ \"title\": \"{{parameters.title}}\", \"lastName\": \"{{parameters.lastName}}\" }"
}

  7. Pick the format from a header

    Match Accept: text/csv at priority 1 and answer JSON for everything else. The same works for API versions in a header, or a tenant id.

Next: Make responses dynamic

Realistic mocks3 min

Make responses dynamic

With response templating, one stub can answer with values taken from the request, so /payments/7 returns payment 7 and /payments/42 returns payment 42.

  1. Turn on Response templating

    In the stub's Response section, tick Response templating (you can see it in the first stub tutorial). Then use placeholders in the body or headers.

    WriteTo get
    {{request.path.id}}The {id} part of a path template
    {{request.query.status}}A query parameter
    {{request.headers.X-Tenant}}A request header
    {{jsonPath request.body '$.name'}}A field from a JSON body
    {{randomValue type='UUID'}}A fresh id
    {{now}}The current date and time

  2. See a full example in JSON view

    Every stub can be edited as WireMock JSON. Select JSON at the top of the editor to see exactly what's stored, conditionals and all.

Learn from examples. Install Dynamic responses — templating from Examples. Each stub explains the technique it uses.

Next: Generate realistic fake data

Realistic mocks2 min

Generate realistic fake data

Instead of "John Doe" in every response, let each call return a believable person, address or company, in any language.

  1. Pick a helper from the Fake data menu

    Open a stub and, under the response body, select Fake data. Choose what you need: a name, e-mail, phone, city, company, product, price and more. MockHub copies the helper, such as {{fake 'Name.fullName'}}, and turns on Response templating. Paste it into the body and save.

WriteGives, for example
{{fake 'Name.fullName'}}Grace Hopper
{{fake 'Internet.emailAddress'}}grace.hopper@example.com
{{fake 'Number.numberBetween' 1 100}}42
{{fake 'Address.city' locale='de'}}Bad Homburg

Imports get it too. Importing an OpenAPI spec fills fields by their name and format, so email gets an e-mail address and createdAt a date. Those values stay the same on every import, so your tests stay stable.

Next: Generate a list of records

Realistic mocks2 min

Generate a list of records

Need 20 customers with names, e-mails and addresses? The data generator builds the JSON for you, once, so every call returns the same data.

  1. Choose the fields and how many records

    In a stub's response, select Generate data. Each row is a field: give it a name and pick what goes in it, from ids and names to prices, IBANs and colours, or type any Datafaker expression. Use dots to nest fields, like address.city. Set the number of records, an optional language, and an optional key to wrap the list in, such as customers. Select Generate, check the preview, then Use as response body.

Fixed or fresh. The generator writes fixed data, which keeps tests repeatable. For new values on every call, use fake data helpers instead. When you create a CRUD resource, Generate fake records fills its starting records the same way.

Next: Build a CRUD API that stores data

Realistic mocks3 minNeeds the editor role

Build a CRUD API that stores data

A CRUD resource is a mock that remembers. POST /customers saves a customer, GET /customers/1 returns it, and PATCH or DELETE change it. No stubs to write per endpoint.

  1. Create the resource

    In Stubs, select CRUD resource. Name it (plural, like customers), choose whether new ids are 1, 2, 3 or UUIDs, and optionally paste some starting records. The preview shows the six endpoints you'll get.

  2. See and edit the records in the Data tab

    The Data tab lists every resource and its records. Search them, add a record as JSON, edit one, delete one, or clear the lot. Records survive restarts and are included in backups.

  3. Call it from your app

    Below the records, Call it lists each endpoint with the project's base path. Lists can be filtered (?city=London), sorted (?_sort=name&_order=desc) and paged (?_limit=10&_offset=20), with the total in the X-Total-Count header.

Mix and match. A CRUD resource is one stub, so you can add more specific stubs next to it, like an error for one id with a higher priority. The AI assistant can create CRUD resources too: ask for "a customers API that stores data".

Next: Simulate slow and failing services

Realistic mocks3 min

Simulate slow and failing services

Real services are sometimes slow or broken. Mock that on purpose to check your timeouts, retries and error messages.

  1. Send a broken response with Fault

    In Response, switch from Respond to Fault and choose what goes wrong: the connection is reset, the response is empty, the body is malformed, or random data arrives and then the connection closes.

  2. Slow it down with Delay

    In Delay, choose Fixed for the same delay every time, Random range for a delay between two values, Realistic for mostly fast answers with an occasional slow one, or Trickle to send the body slowly in pieces.

  3. Fail only some calls

    In Failures, enter a percentage, for example 10% of calls, and choose an Error status such as 503 or a Network fault. Those calls fail at random and the rest get the normal response. Failed calls carry the header X-MockHub-Simulated-Error: true, so you can tell them apart in your logs. The stub list shows a 10% fail tag.

Fails once, then works. Combine a fault with a scenario to test retries, like the Flaky stub in the Resilience testing example. To slow down every project at once, set a Global delay on the Server page.

Next: Behave like the real API

Realistic mocks4 min

Behave like the real API

A real service answers unknown paths with its own error, limits how often you call it, slows down when it's busy and decides which websites may call it. Set all of that once per project, in Settings → Runtime behaviour.

  1. Answer unknown paths with your own error

    Turn on Default response and write the status, headers and body the real service sends for a path it doesn't know. With Use templates on, {{request.method}} {{request.path}} name the call. Every stub is still tried first.

  2. Add a rate limit and latency

    Turn on Rate limit, for example 60 requests per minute. Calls over it get 429 with Retry-After and X-RateLimit-* headers, so you can test your back-off. Under Latency, choose Random range and tick Get slower under load to make answers slower as a load test pushes harder. Then Save.

  3. Decide which stub wins

    In the Stubs tab, click Show matching order. Stubs are tried from the top and the first match answers. Drag a specific stub, like an error for one id, above a general one, then Save order.

Browser apps. Under CORS, list the websites that may call the mock, or choose Fail on purpose to see how your frontend handles a blocked call. An IP allow list keeps a mock to your CI runners or VPN. The rate limits, CORS and default response docs have the details.

Next: Send webhooks and serve files

Send webhooks and serve files

Some APIs answer later through a callback, and some return files. Mock both.

  1. Add a webhook under Then call

    In a stub's Then call section, select Add webhook. Set the method, the URL to call, headers, a body and an optional delay, for example a payment callback two seconds after POST /payments. Use Insert dynamic value to pass values from the request, such as {{jsonPath originalRequest.body '$.id'}}, or from the response the stub sent, such as {{jsonPath originalResponse.body '$.id'}}. Choose Forward incoming request to pass the request on unchanged.

  2. Check what was sent

    Call the stub, then open the project's Callouts tab. Each callout shows the URL, the body sent, the answer and the time it took. A blocked address or a template mistake shows up in red. With the AI assistant on, Ask the assistant to fix it explains the problem and stages a fix.

  3. Or wait for the partner's answer

  4. Upload response files

    On Import & export, use Response files to upload PDFs, images or large JSON, up to 10 MB each. The list shows how many stubs use each file.

  5. Serve a file from a stub

    In the stub's response, choose File as the body and pick the file, or upload one right there. The Content-Type header is set to match.

Next: Mock OAuth, validate input, mix responses

Realistic mocks4 minNeeds the editor role

Mock OAuth, validate input, mix responses

Issue real signed tokens your app can verify, answer 400 when a request is wrong, and make an endpoint fail now and then, all without writing code.

  1. Start from an auth template

    On the Stubs tab, open Start from a template and pick Auth & validation. OAuth token endpoint issues an RS256 token for the user in the request, JWKS public keys lets your app verify it, Who am I reads the bearer token's claims, and Validate the request body answers 400 when a field is missing.

  2. Insert token helpers from the picker

    In any response body, open Insert dynamic value and search jwt. {{jwt}} signs a token with the server's key, or with your own secret for HS256. {{jwtDecode}} reads a claim from the Authorization header. The Validation group adds required, isEmail and check, which stop the response and answer {"error": "…"} with a 400, or the status you give.

  3. Add other responses with weights

    Under Other responses, click Add another response. Give the main response weight 9 and a 503 weight 1, and about one call in ten fails. Each one can change the status, headers and body, and templating still applies. The X-MockHub-Weighted-Choice header says which one was picked.

More in the docs: JWT & OAuth, Validation and Weighted responses.

Next: Move from WireMock

Bring in what you have3 min

Move from WireMock

Already have a folder of WireMock mappings, maybe inside a Spring Boot app or a standalone server? Bring it over as it is. Your services keep calling the same URLs.

  1. Zip the folder

    Zip the folder that holds mappings and __files. Where it sits inside the zip doesn't matter, so you can zip a whole src/test/resources folder.

    zip -r wiremock.zip src/test/resources/wiremock

  2. Import it into a project

    Create a project, open Import & export, choose WireMock folder and drop the zip in. Every mapping file becomes stubs, and every body file is copied into the project, sub-folders included. If a mapping points at a file that isn't in the zip, MockHub lists it so you can add it under Response files.

  3. Answer at the root

    Normally a project answers under its base path, like /orders/…. A WireMock server answers at the root. In the project's Settings, turn on Answer at the root: stubs then match exactly the paths they had before, and templates like {{request.pathSegments.[0]}} count the same way. Paths that start with another project's base path still go to that project, and its request log stays separate.

  4. Point your services at MockHub

    Swap the old WireMock host for MockHub. Nothing else changes: same paths, same bodies, same templates.

Carries overNotes
Files with one mapping, or {"mappings": [...]}Both, in any sub-folder of mappings
Body filesCopied into the project; bodyFileName is updated for you
Matchers, priorities, scenarios, faultsUnchanged
Response templates and transformerParametersUnchanged. Templating that ran globally needs "transformers": ["response-template"] on the stub
Proxies with proxyBaseUrlUnchanged; MockHub needs network access to the target

One root project per server. Only one project can answer at the root. Everything else keeps its own base path. If the stubs used to be created at runtime through /__admin/mappings, that still works: send the same calls with a MockHub token.

Next: Move a whole mock repository

Bring in what you have5 min

Move a whole mock repository

Many teams keep a Git repository of WireMock mappings: thousands of stubs in a folder per team, files that hold many stubs each, body files referenced as ./team/service/file.json, and a pipeline that restarts WireMock after every merge. MockHub takes it over as it is. Every response stays the same, and changes go live without a restart.

A typical repositoryExample
Mappings in a folder per team or servicemock/mappings/acme/orders/orders.json
Several stubs in one file{"mappings": [ … ]}
Body files with relative paths"bodyFileName": "./acme/orders/order-42.json"
File names built from the request"./acme/orders/{{request.pathSegments.[1]}}.json"

  1. Choose how to bring it over

    Run on the folder if you want the quickest switch: MockHub serves the stubs straight away. Import a zip if MockHub is already running for other teams: the stubs go into a project of their own. Both give the same responses as your old WireMock.

  2. Option 1: run MockHub on the folder

    Copy the folder that holds mappings and __files and start MockHub with the copy as its data folder. Use a copy, not your Git checkout, because changes made in MockHub are written back to these files.

    cp -R acme-mocks/mock /srv/mockhub-data
docker run -d --name mockhub -p 8080:8080 \
  -e MOCKHUB_USERS="admin:change-me:admin" \
  -v /srv/mockhub-data:/data abhaypratap/mockhub

    Every stub answers at once on the same URLs. They're listed under Server → Stubs outside any project. To manage them in the UI, move them into a project that answers at the root. One request per stub does it:

    API=http://localhost:8080/__admin/mockhub/api
AUTH="admin:change-me"
PROJECT=$(curl -s -u $AUTH $API/projects -H 'Content-Type: application/json' \
  -d '{"name":"Acme mocks","root":true}' | jq -r .id)
curl -s -u $AUTH $API/stubs/unassigned | jq -r '.[].id' | while read id; do
  curl -s -u $AUTH -o /dev/null -X POST "$API/projects/$PROJECT/adopt/$id?prefix=false"
done

  3. Option 2: import it as a zip

    Zip the folder, create a project, turn on Answer at the root in its Settings, then open Import & export → WireMock folder and drop the zip in. A zip can hold up to 20,000 files and 200 MB.

    cd acme-mocks && zip -r ../acme-mocks.zip mock

    Folders are kept, so ./acme/orders/order-42.json and file names built from the request keep working. Empty body files are fine. If a mapping points at a file the repository doesn't have, MockHub lists it, so you can fix it before anyone notices.

  4. Check that nothing changed

    Run the old WireMock and MockHub side by side for a day and send the same calls to both, or point one test suite at each. The Requests tab shows every call, and near misses explain any request that didn't match.

  5. Switch over and drop the restart step

    Point your services and tests at MockHub. Changes made in the UI or through /__admin/mappings go live immediately, so the pipeline job that restarted WireMock after each merge isn't needed any more. Keep a copy with Backup & restore, or export the project as WireMock mappings whenever you want it back in Git.

Carries overHow
Files with many stubsServed as they are. When you change one of their stubs, MockHub splits that file into one file per stub in the same folder.
Which stub wins a tieWhen several stubs match with the same priority, the winner stays the same after edits and restarts.
./ and / paths, folders, templated file namesUnchanged
Very long URLsSaved with a shortened file name; the stub itself is unchanged
Scenarios, faults, delays, proxies, transformerParametersUnchanged

Tried on a real repository. We moved a team's repository with more than 2,000 stubs and 2,000 body files both ways and sent the same request for every stub to the old WireMock and to MockHub: every response matched, before and after a restart.

Snapshot and roll back

Save a project's mocks before a release, a demo or a risky change, see exactly what changed since, and put it back in one step. The same tab copies one project into another, such as dev into qa.

  1. Take a snapshot
